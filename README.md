# GameTune Agent

GameTune Agent 是一个使用 PySide6 构建的 Windows 游戏性能调校智能体，根据实测反馈进行受约束规划。先记录环境并采集基线，再由模型从程序校验的候选中选择实验，根据玩家实际采用的配置与实测结果调整下一步。可以同时改多项画质，程序按整组配置评价；单项对比仅用于判断具体原因。程序负责指标、有效性和保留或回滚判断；游戏内设置由你实际修改并确认，未连接模型时使用本地规则。

当前版本实现任务创建、瓶颈证据展示、诊断实验录入、历史记录和报告界面，并包含可独立测试的确定性核心：CSV 数据导入、逐帧指标计算、证据分析、实验规划、效果评估与 SQLite 持久化。多轮评估会比较当前已接受配置，只有达到重复测试门槛且确认实际执行的结果才能成为最佳已验证配置。模型 API 是可替换的建议选择与解释层，不影响本地闭环运行，可在“模型设置”页面直接填写兼容接口并选择思考模式。

## 安装与运行

### Victoria 3 模块

**当前界面 v2026.10.29.4：配置独立保存，自由对比。**

- 运行 `python victoria3_app.py`，侧栏使用「配置库」「配置报告与对比」。每条配置记录包含自己的设置快照、测试、传感器信息、来源及模型解读，没有固定的优化前/后角色。
- 性能测试自动识别实际运行的设置，将每次采集追加到该配置；设置、设备或版本改变后使用另一条配置记录。可使用「把当前设置另存为一条新配置记录」区分同样设置下的不同测试场景，建议填写场景标记。
- 在「单个配置报告」中查看、重命名或导出一套配置。在「自由对比」中任意选择 A、B，支持交换方向，查看指标差异与图形设置对照。对比不移动、合并或覆盖任何原始配置数据；场景、设备、版本、时长和重复性不足会提示。
- 模型可以解读单个配置，也可以解读当前选择的 A/B 对比。单配置解读与独立对比解读分别保存；解读不能修改测试数值。更换选择或采集更新后，过期模型回复不能覆盖新数据。
- 旧成对报告里的两侧实测会各自迁移成独立的历史配置记录，原数据库记录和文件保留；重复启动不重复迁移。一键优化和恢复只更新游戏设置、配置快照与操作记录，不再生成绑定前后的报告。

下述旧成对报告说明保留用于原型与旧数据兼容；独立入口现在使用上面的配置工作流。

Victoria 3 现在提供独立窗口，运行 `python victoria3_app.py`，不与 CS2 工作区一起显示。侧栏分为「概览、一键优化、性能测试、历史记录、最终报告、模型设置」，沿用 CS2 桌面程序的视觉组件。原 `app.py` 保留 CS2 入口，Victoria 3 导航不再展示在该入口。

独立窗口「模型设置」复用现有 `ModelProvider` 协议和兼容 Chat Completions 适配器，可填写地址、密钥、模型名及思考模式，也支持已有 `GAMETUNE_API_*` 环境变量。报告页明确同意后才将硬件型号、图形设置与实测摘要发送到所配置 API，不包含存档内容、文件路径或密钥。`agent/victoria3_model.py` 的 `explain_victoria3(provider, report)` 接受任意符合协议的 Provider，失败或未配置时返回本地建议。模型结果独立标记，不修改实测指标、不执行设置、不决定实测是否有效。密钥仅驻留当前进程。

侧栏选择「Victoria 3 优化」（截图索引 6）。默认进入简化模式，无需填写测试表格：

- 自动读取 Windows 文档目录中的游戏设置、最近一次启动日志中的版本/硬件及本地存档列表，支持重定向的文档目录。日志信息可能滞后，不作为实时遥测或瓶颈结论。
- 选择温和方案（保持画面比例，降低一档分辨率）或轻量画面方案（另关闭多重采样、各向异性过滤、折射及阴影）。后者的值依据本机 1.13.11 版 `clausewitz/compound_settings.txt` 核对，属于画质取舍试用方案，不保证提升跑日速度。
- 预览改动后点击「备份并应用方案」，再点击「启动 Victoria 3」向 Steam 发送启动请求。应用与恢复都要求退出游戏，不会自动终止游戏进程。
- 自动备份保存在游戏用户目录的 `gametune-backups/` 中，可从列表恢复。设置写入使用原子替换；预览过期会拒绝应用，恢复只处理本次修改的图形字段，保留其他选项。若这些字段后来被另行修改，会提示冲突并拒绝覆盖。
- 「一键恢复优化前」自动查找最近一次未恢复优化的备份，不必记忆原始值或选择文件。按钮旁显示该次优化前的图形设置；游戏运行时仍需先退出。硬件配置从未被更改，恢复只处理游戏图形设置。
- 扫描与预览只读；工具不修改存档、不关闭进程、不更改系统设置。应用成功仅代表配置已写入，不代表性能收益已验证。

需要量化跑日速度时，展开「高级性能测试」。模块与 CS2 共用桌面程序及 SQLite 数据库，使用独立表保存实验，避免将跑日速度混入 FPS 评分。存档可从自动发现的列表选择，版本及图形配置会自动带入；其他受控实验条件仍需确认。

### 自动优化报告

### 内置 PresentMon 采集

独立窗口「性能测试 → 自动采集 FPS」内点击「一键准备」，即可从官方 GitHub 下载固定版本 PresentMon 2.6.0 控制台版并验证发布的 SHA-256。无需手工导入 CSV，也无需安装驱动。许可证见 `third_party/PresentMon-LICENSE.txt`。

先启动游戏并载入固定存档，选择「采集优化前」、确认场景与配置，点击开始；8 秒后采集，默认 60 秒。结束后帧时间自动计算成平均 FPS 和 1% Low，并写入当前报告。退出游戏应用方案，再启动并载入相同场景，选择「采集优化后」重复。每侧至少三次独立测试才有重复性证据，每次重新载入同一存档。可取消；失败、超时、配置变化或有效时长不足的数据不会自动关联报告。

原始 CSV、筛选后的 CSV 及采集日志保存在 `.data/captures/`，工具保存在 `.data/presentmon/`。仅定位一个 `victoria3.exe` 进程，使用帧数最多的交换链，不合并多个独立渲染流。每个采集文件只算一次测试；重复测试按每次结果的中位数和波动汇总。优化前记录随匹配的原始配置自动带入应用后的报告。不会根据 GPU Busy 的毫秒值推断 GPU 占用率。

采集工具实际启动后，主窗口自动最小化，桌面保留不抢焦点的置顶倒计时：先显示 8→1 秒准备时间，再显示采集剩余时间（默认 60 秒）。独占全屏游戏可能遮挡桌面提示。完成、失败或取消后收起倒计时，自动恢复主窗口原来的普通/最大化状态，展示结果或可复制错误；下载工具时不会自动最小化。采集页与一键优化页提供「复制当前提示 / 报错」按钮；独立窗口的说明标签可鼠标选中复制，报告和模型解读支持原生文本复制。

ETW 权限不足时会明确提示，不会自动提权或修改权限。PresentMon 本身不提供游戏日期；下述本地 OCR 可补充跑日速度参考测量，严格受控比较仍使用「高级跑日测试」。

### 同步硬件监测与游戏日期识别

v2026.10.29.1 起，在 FPS 采集期间同步读取整机 CPU 占用（Windows `GetSystemTimes`）、NVIDIA GPU 占用/温度/功耗（驱动自带 `nvidia-smi`）。排除 8 秒准备期，记录逐样本时间、均值、峰值、有效样本数和数据来源。数值为整机/整块显卡的负载，包含后台程序，并非游戏进程独占。多卡无法唯一匹配、驱动返回 N/A、读取失败会分别标明，不填虚构的零。

CPU 温度读取已运行的 LibreHardwareMonitor/OpenHardwareMonitor WMI 温度接口，优先 CPU Package/Tctl/Tdie，回退到 CPU 核心最高温度；不会把主板或 ACPI 热区温度作为 CPU 温度。没有服务时报告显示「设备或接口不支持」及缺失原因。本版不安装内核驱动或更改安全设置。

跑日速度可选择本地 Windows OCR：在采集页点击「准备日期识别组件」，从 PyPI 安装固定 3.2.1 版 PyWinRT 投影到 `.data/ocr-runtime/`。点击「框选游戏日期区域」后，切回游戏、把鼠标移到日期处使其完整显示，再按临时截图键 F8（被占用时提示 F9/F10）。程序冻结鼠标所在显示器的游戏画面，再显示不抢焦点的框选层；拖动框选日期，右键取消。快捷键用完或等待超时即注销，仅保存选区比例。核对校准日期后开始采集，并保持日期可见。勾选日期识别后，每次采集仅在 Victoria 3 位于前台时对日期区域采样；截图仅在本机短暂存放，识别后删除，不上传，不读游戏内存，不控制游戏。当前支持 `1900年1月15日`、`1900.1.15` 等日期形式。

跑日参考值按识别到的公历整数日期差 / 实际秒数计算，存在不足一天的边界误差；日期回退、样本不足或暂停时不生成虚构速度。它与高级受控重复实验分开标注，不能据此宣称已验证收益。更改显示器、缩放或日期位置后需要重新框选。独占全屏阻止截图、OCR 语言组件缺失或格式不支持时保留具体原因。

传感器摘要与原始样本保存在对应的 `.sensors.json`，每次采集文件记录日期识别样本。报告展示均值、峰值、来源、样本数以及「未采集 / 设备或接口不支持 / 采集失败」；温差使用摄氏度，利用率差使用百分点。旧报告不回填新测量值。

若日志明确显示 `failed to start trace session: access denied`，可在自动采集页点击「以管理员权限打开采集页」，由用户确认 Windows UAC 后打开带「管理员」标题的新窗口。新窗口显示完成并回传一次性本地就绪确认后，原窗口自动关闭；取消授权、启动失败或等待超时时保留原窗口。交接中暂时禁用原窗口操作，避免新增任务阻挡关闭。此操作仅应用户点击发起，不修改用户组、账户权限或系统设置；会保留 Qt 运行时搜索路径，避免管理员进程找不到依赖。其他退出错误展示实际退出码和日志，不统一误报为权限不足。

在 Victoria 3 页面的「优化报告」标签中直接查看本机诊断、性能对比和历史报告；点击「查看优化报告 / 性能对比 / 历史报告」也会切到该标签。应用或恢复后自动生成/更新报告并切换显示，无需打开独立窗口。报告保存到 SQLite 的 `victoria3_reports` 表，可重启后查看，支持导出 HTML 与 JSON。

报告包括本机 CPU/GPU/内存/系统及其日志来源、优化前后图形设置快照、实际变更、备份位置、操作记录、各指标前后对比及高级建议。硬件型号不用于估算 FPS。没有历史测量值的项目不回填，传感器不可用或失败会单独说明。

在报告窗口可分别导入前后 FPS CSV（格式与 CS2 一致）。确认数据来自对应配置、场景及采集方法一致后才显示变化率；少于三次或波动较大的数据仅供参考。应用前诊断报告导入的基线，仅在图形配置、设备和游戏版本匹配时转入本轮应用报告。高级跑日实验仅在前后 JSON 图形配置与报告匹配且测试条件一致时关联，不会将模拟速度提升当作 FPS 提升。恢复后的候选数据标记为历史配置。

v2026.10.29.3 修复基线转移：核对图形设置、设备及游戏版本，无关的音量、主题和界面记账字段变化不会丢弃基线；保留原始采集文件、传感器摘要及来源报告 ID。历史下拉列表显示前后各有几次测试。旧版本已分散的数据可在含优化后实测的报告中点击「找回已有优化前数据」，匹配配置并确认同一场景后关联，原始记录均保留。重复测试不足仍不宣称收益已验证。

模型解读使用独立 `QThread.run()` 计算，通过明确的 GUI 主线程 Slot 接收；无后台线程写入控件。解读保存到对应报告，重新打开和导出可查看。请求期间报告或配置改变时丢弃过期解读，不覆盖已保存的实测数据；模型失败回退本地建议。

1. 选择起始 `.v3` 存档，填写版本/校验码、有序模组与 DLC、起止日期、速度档位和固定环境（硬件、供电、散热、视角、缩放、自动存档规则）。存档使用 SHA-256 校验前后一致性。
2. 每次重新载入该存档，固定预热流程，计时推进相同游戏天数。每组至少三次，填写游戏天数与实际秒数；平均 FPS 和 1% Low 可选，但填写时需每次均记录。
3. 填写实际配置并保存基线，依据实验提示只调整一个变量，记录原值、新值及恢复方法。替换表格为复测数据，确认已经执行后评估。
4. 报告独立显示游戏天/秒的中位数及变化率。前后条件不同会拒绝比较；波动超过 5%、收益不足 5% 或未确认执行会要求复测；模拟速度或记录的 FPS 指标下降至少 5% 会建议恢复。收益至少 5% 且通过上述检查才建议保留。
5. 历史记录可重新载入基线和报告，报告可导出 JSON。各次比较始终相对所载入的基线，不自动晋升候选配置。

CSV 表头为 `game_days,elapsed_seconds`，可另加 `avg_fps,low_fps`；每行代表一次独立测试。高级测试中的设置参考按钮只读，简化模式的应用按钮才会写入配置。支持 PresentMon 帧时间、可用硬件传感器和可选日期 OCR 自动采集，但未验证真实游戏性能收益。

```powershell
python -m pip install -r requirements.txt
python app.py
```

程序会先打开游戏选择页，选择 Counter-Strike 2 或维多利亚 3 后进入对应工作区，不需要浏览器或本地 Web 服务。窗口顶部的“返回游戏选择”可切换游戏，已打开工作区的状态会保留；关闭游戏窗口也会返回选择页，在选择页关闭窗口才会退出程序。采集、日期识别或权限切换进行中时，请先结束操作再切换。

也可使用 `python app.py --game cs2` 或 `python app.py --game victoria3` 直接进入对应游戏。原有 `--screenshot` 与 `--page` 截图参数仍然可用。

维多利亚 3 工作区提供短暂的页面与标签过渡、侧栏位置指示，以及高级测试的展开与收起动画。关闭 Windows 的客户端区域动画效果后会减少动态效果，也可在启动前设置 `$env:GAMETUNE_REDUCED_MOTION = "1"` 禁用这些动画；切换和展开仍然可正常操作。

也可以直接双击项目根目录的 `GameTune.exe`，无需手动运行 Python。单文件 EXE 已包含 Python、Qt 和知识库，首次启动需要等待解压；任务记录保存在 EXE 旁的 `.data/gametune.db`，放在当前项目根目录时会继续使用原来的记录。移动 EXE 时，请同时保留旁边的 `.data` 文件夹，并选择可写目录。模型设置仍保存在当前 Windows 用户的应用数据目录中，密钥不包含在 EXE 内。

源码修改后需重新打包。安装 `requirements-build.txt` 后双击 `build_exe.bat`，或在根目录执行 `python -m PyInstaller --noconfirm --distpath . --workpath .qa/build GameTune.spec`；输出为根目录的 `GameTune.exe`，构建中间文件位于 `.qa/build`。打包仅收集源码依赖和 `knowledge/*.json`，不会包含本地数据库、截图或已保存的 API 配置。

运行核心测试：

```powershell
python -m unittest discover -s tests -v
```

想快速检查常见使用流程，可双击根目录的 `run_scenarios.bat`，或运行 `python run_scenarios.py`。它会自动执行 15 个模拟流程与边界样例、3 个界面操作样例，无需手动填表，不读取正式测试数据或调用真实模型接口；结果保存到 `.qa/scenario-results.txt`。各样例的数据和预期行为见 [测试样例说明](docs/TEST_SCENARIOS.md)。

## 界面流程

首次启动时，“当前调校”提供创建入口，不会把预填设置当作已完成的测试。左侧始终提供六个页面和“使用说明”，完整操作说明见 [界面使用指南](docs/UI_GUIDE.md)。

1. 在“新建调校”先记录设备、游戏设置、场景和目标，再进入基线测试；准备任务时不需要知道帧率。
2. 使用相同场景与设置测两次，每次至少 60 秒。录入逐次结果，波动超过 5% 时补测第三次，再保存基线。
3. 在“当前调校”查看逐次测试表现、本次调整与测试条件，可展开分析依据了解方法和有效标准。建议尚未代表已执行或已获得收益。
4. 在“当前实验”按页面要求补充设置、选择验证目标或录入测试。按实际采用的设置填写，可以同时调整多项画质；程序会从这组配置继续规划，不会为了验证旧建议强制恢复画质。单项诊断或原计划验证仍按对应测试条件判断。
5. 在“测试记录”检查逐次结果，或打开以前的任务继续验证；在“配置与报告”查看与基线可比较的已验证配置及收益。未形成可比较记录时显示“待验证”。
6. “模型设置”为可选功能：AI 解释结果并从程序校验过的候选中选择建议；指标、有效性和保留或回滚由程序判断。连接失败时回退到本地规则。

界面采用 Claude 风格的暖白工作区、浅暖灰侧栏和陶土色主操作，搭配宋体标题与清晰的无衬线正文。调校页按真实记录展示逐次帧率，缺少逐次数据时显示说明；下拉框统一采用圆角和向下箭头，支持键盘选择。动画用于反馈切换和通知，重复切页不会重播同一组入场动画。

## 测试数据与验证口径

- 汇总 CSV 使用 `avg_fps,1%_low,gpu_usage` 表头；每行代表一次独立测试，GPU 占用率列可省略。导入保留逐次结果、中位数和极差占中位数的百分比。
- 逐帧 CSV 支持 `frame_time_ms`、`frametime` 或 `MsBetweenPresents` 等毫秒列，至少需要 100 个有效样本。一个采集文件只算一次测试，不把帧数当成重复次数。
- 平均 FPS 为有效帧数除以总帧时间；1% Low 为最慢 1% 帧的平均帧时间换算成 FPS。不同采集工具的同名指标可能使用不同口径，应保持工具与采集模式一致。
- 非数字、非有限数、非正帧时间和缺失必要字段会提示具体 CSV 行号。`gpu_busy` 不被当作百分比占用率导入。
- 基线先完成两次；如果两次结果差异超过 5%，再补第三次。候选设置先做一次筛选，明显退步会立即建议回滚；没有明显下降时继续累计到三次有效运行后才确认收益。有逐次数据时检查波动；手动填写的汇总值和重复次数不包含可验证的波动证据，但连续提交每次测试次数为 1 的结果会按同一配置累计，应在真实采集后复核。

演示和自动化测试使用临时数据库与模拟模型接口，不代表已经完成真实游戏性能提升验证。

分辨率提供常用 16:9、16:10 和 4:3 候选值，也可以直接输入自定义的“宽 × 高”数值。实际可选项取决于显示器、显示模式和显卡缩放设置；分辨率对照实验会优先选择同宽高比的下一档，避免因改变画面比例干扰瓶颈判断。

CS2 任务会按游戏简体中文菜单记录显示模式、游戏最高FPS、V-Sync、全局阴影效果和动态阴影。当前游戏已将全局阴影效果与动态阴影范围拆成两个设置，因此阴影实验必须保持动态阴影不变；竞技任务默认记录“动态阴影：全部”，避免把可见性变化误当作单纯画质收益。游戏最高FPS使用具体数值，`0` 表示不限制。显示文本与当前 CS2 简体中文资源保持一致，内部稳定值保留以兼容已有任务。

高级视频设置还会完整记录当前视频值预设、增强角色对比度、NVIDIA G-Sync、NVIDIA Reflex 低延迟、AMD Anti-Lag 2.0、菜单最高FPS、多重采样抗锯齿、模型/贴图细节、贴图过滤模式、光影细节、粒子细节、环境光遮蔽、高动态范围和 Fidelity FX 超级分辨率。显卡厂商专属选项允许选择“此设备不可用”。

CPU 和 GPU 使用 `knowledge/hardware.json` 中的标准型号目录，并区分桌面与 Laptop 型号。目录不显示或推断固定性能等级；超频、功耗限制、散热、内存和游戏负载都会改变实际表现，因此瓶颈判断只使用当前设备的实测遥测和对照实验。列表末尾可以选择自定义型号。

选择任一 Laptop CPU/GPU 或“自定义 Laptop 型号”后，任务页面会显示笔记本补充信息：持续 GPU 功耗、独显直连/混合输出、供电性能模式和散热模式。平台模式本身只构成待验证线索；有 GPU 实测证据时，本地规则优先考虑对应的画面负载验证，接电平衡模式不会固定成为第一步。限帧和测试条件等关键干扰仍需先排除。

## 实验选择与反馈验证

“当前实验”显示选择来源、依据与待验证假设，可展开“查看候选与历史反馈”查看本轮合法候选、已选项、最近结论及未解决问题。有多个候选且模型可用时调用模型比较；只有一个候选时直接使用本地计划。模型失败会明确记录回退，不算作模型成功选择；调用耗时和选择上下文随任务保存，重启后可查看。

下一轮规划同时接收逐项实验记录与结构化反馈摘要，区分无效测量、补测、诊断线索、已验证收益和无收益恢复。已验证无收益的动作会跳过，无效测量不会被记成“该项无收益”；补测继续原方案，不因刷新或重启更换调整。课程验证先聚焦 CS2，不扩展多智能体或复杂搜索。

本地规则与模型对照工具、真实案例采集步骤和证据要求见 [智能体闭环验证](docs/AGENT_VALIDATION.md)。对照在同一组候选和历史上记录合法性、重复无收益动作、人工可接受标注及耗时，不预设模型优于规则；回放结果不能代替真实游戏案例。

## 核心模块

- `models/schemas.py`：任务、基准测试、证据、实验计划和决策结构。
- `tools/import_benchmark.py`：兼容逐帧时间或多轮汇总 CSV。
- `tools/calculate_metrics.py`：平均 FPS、1% Low、中位数、目标完成度和按模式加权的实际变化。
- `tools/analyze_evidence.py`：区分表现症状与可能原因，并把缺失条件计入证据支持程度。
- `agent/planner.py`：根据证据选择下一次单变量实验。
- `agent/evaluator.py`：保留、撤销、复测或结束判断。
- `agent/controller.py`：协调工具并记录完整闭环。
- `agent/state_machine.py`：约束等待输入、分析、等待复测、评估和完成状态转换。
- `agent/validator.py`：在展示建议前校验轮次、必要字段、设置名和允许值。
- `agent/api.py`：模型 Provider 协议、统一请求/响应以及兼容型 HTTP 适配器。
- `agent/prompts.py`：结构化提示词和模型 JSON 输出校验。
- `agent/explainer.py`：模型解释调用与离线回退。
- `storage/repository.py`：SQLite 任务、测试和决策记录。
- 每条测试记录包含配置快照和“已确认执行”标记；SQLite 另外保存当前配置、最佳配置及工作流轮次，控制器可通过 `restore_task(task_id)` 恢复任务上下文。
- `knowledge/cs2.json`：第一版 CS2 可调整项规则。

正式优化在平均 FPS 和 1% Low 均达到各自目标的 95% 时视为进入目标范围；高于目标也算达成。目标完成度仍使用竞技 35%/65%、平衡 50%/50%、视觉 60%/40% 三组固定偏好，并把超过目标的指标封顶为 100%，只用于显示距离目标还有多远。候选配置是否保留则使用未封顶的实际 FPS 变化：先检查明显退步，再按模式权重合并平均 FPS 与 1% Low 的变化；加权变化太小会要求复测，避免微小分差直接改变配置。视觉模式还会阻止已记录的分辨率或画质档位下降被自动当成优化结果。

## 模型 API 预留接口

核心优化逻辑不依赖模型。模型从程序生成并校验的候选中选择建议，并把结构化决策解释成自然语言；调用失败或输出不合法时，系统自动使用本地规则和说明。

实现其他服务时，只需满足 `ModelProvider`：

```python
class MyProvider:
    name = "my-provider"

    def complete(self, request: ModelRequest) -> ModelResponse:
        # 将 request.messages 转换成目标服务需要的格式
        # 调用服务后统一返回 ModelResponse
        ...
```

控制器注入方式：

```python
controller = GameTuneController(".data/gametune.db", model_provider=MyProvider())
explanation = controller.explain(task, decision, evidence=evidence, plan=plan)
```

项目还提供了不依赖第三方 SDK 的 Chat Completions 兼容适配器。配置使用环境变量，不要把密钥写入源码：

```powershell
$env:GAMETUNE_API_BASE = "https://your-service.example/v1"
$env:GAMETUNE_API_KEY = "your-api-key"
$env:GAMETUNE_MODEL = "your-model-name"
$env:GAMETUNE_API_TIMEOUT = "30"
$env:GAMETUNE_REASONING_EFFORT = "medium"
```

也可以不设置环境变量，直接在桌面端“模型设置”页面填写并测试。填写 API 地址和密钥后可点击“获取模型”，程序会请求兼容接口的 `/models` 并把模型 ID 放入可编辑下拉框。勾选“记住本机 API 配置”后，地址、模型、超时和思考模式保存到用户配置目录，密钥使用当前 Windows 账户的 DPAPI 保护后保存；取消勾选或点击“清除已保存配置”即可移除本机配置。环境变量优先于本机保存配置。思考模式关闭时不发送 `reasoning_effort`；低、中、高分别发送 `low`、`medium`、`high`。未设置环境变量且没有本机配置时，系统保持离线运行；只设置一部分环境变量时会明确报告缺少的配置项。

### CS2 Benchmark 日志监听

在 Steam 的 CS2 启动选项中加入 `-condebug`，重启游戏。进入 GameTune 的 CS2 复测页，点击“选择游戏日志”（会先尝试定位 Steam 库），选择游戏目录下 `game/csgo/console.log`，并在跑 Benchmark 地图前点击“开始监听”。监听会跳过已有历史，只读取新追加的 `[VProf] FPS: Avg=..., P1=...` 行；跑完后自动带入本次 Avg/P1，核对实际配置和测试时长，再点“保存并分析”。无需安装游戏内插件，也不会修改启动项或替你操作游戏。

一条完整的 VProf FPS 摘要算一次独立运行；多条结果排队等待提交，不覆盖未保存结果。保存保留原始小数精度，GPU 占用保持未知。原始性能摘要保存在 `.data/captures/cs2/`，只留 VProf 性能摘要，不复制完整控制台日志。P1 使用游戏报告原值，不把它伪装成程序自行计算的低帧指标；前后比较应使用相同测量来源和相同测试场景。手动修改帧率后按手填数据处理，不能继续冒充原始日志结果。普通下一轮页面重建会延续监听；重新打开应用或切换任务后需重新开始监听。


#### 一键跑图并监听

CS2 复测页新增“一键跑图并监听”，使用 Dust2 Benchmark 创意工坊地图（ID `3240880604`，需要事先订阅并下载）。游戏未启动时，程序先建立日志监听位置，再通过 Steam 使用 `-condebug -console +map_workshop 3240880604 de_dust2` 启动游戏；不必手动添加启动参数，也不改 Steam 保存的启动选项。日志尚未生成时会等待创建，不遗漏启动后第一条结果。

游戏已启动时，程序切换到经过进程身份核对的 CS2 窗口，使用默认 `~` 键尝试打开控制台，再发送一次随机 `echo` 回执。只有在日志中读到这条回执且 CS2 仍在前台，才发送固定的地图指令；随后等待地图加载标记和 VProf 结果。请预先启用开发者控制台并使用默认控制台按键；游戏已打开但没有启用日志时，需要退出后使用一键启动。窗口焦点不正确、按键被系统拦截或回执超时会显示失败，不会宣称跑图成功。点击“停止监听”会取消尚未发出的宏步骤，已经发给游戏的加载指令不会被撤销。该功能不使用剪贴板、不安装 AutoHotkey、不注入游戏，也不会自动结束游戏进程。


### 使用历史记录分析影响

下一步规划和结果解释会从本任务数据库的实验历史计算实际变化幅度，而不只读取“保留 / 回滚 / 复测”状态。单项设置与整组配置分别排序，保留比较记录编号、前后配置、平均 FPS 和 1% Low 变化，以及观察或已验证状态。同一轮累计记录只取最近的有效版本，后来的无效提交不会覆盖此前有效观察。多项设置同时变化不拆分贡献，场景变化、已知配置缺失或非有限指标不进入影响排序。

有效但尚未达到确认次数的结果可以用于提出下一步方向，不会被当作无效数据；它仍不能直接成为最佳已验证配置。候选与历史记录的前后档位及其他配置一致时，离线排序也会优先参考已观察收益、降低无收益或下降方向的优先级。AI 收到相同的历史影响摘要，结果说明会展示影响较大的历史改动；本轮可比性与收益确认仍单独判断。


### 设置影响权重

当前实验右侧可点击“查看各设置影响权重”。权重从现有测量计算，不手工指定：外部数据对每个设置分别计算 `(最大 FPS - 最小 FPS) / 最大 FPS` 的平均帧率与低帧跨度，按任务模式的指标偏好加权，再在同一测试来源的已测设置中归一为 100%。竞技模式使用平均 FPS 35%、低帧 65%；本机历史则使用各设置最大已观察变化的绝对幅度，单独归一并标注是否确认收益。仅一项本机数据得到 100% 时，表示本机已测项目仅这一项，不代表其他设置没有影响。

权重表示影响程度，不表示提升方向、预计收益或组合贡献。外部测试来源之间、本机与外部之间不混合归一；缺失分辨率、显卡模式等数据时显示“未测”，不编造零权重。模型会收到权重及来源说明；本地规划只在原有可用候选内、外部同时测过原档位和新档位且该步骤有改善方向时，用权重辅助同优先级排序。有效本机记录、当前测试条件及计划校验仍优先。外部参考来自单平台社区测量，低帧指标是来源报告的 1% Low Average，不与游戏 VProf P1 混作同一测量。
