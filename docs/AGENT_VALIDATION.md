# 智能体闭环验证

本轮聚焦 CS2 的“选择实验 → 获取反馈 → 调整计划”。程序生成并校验候选，模型结合目标和实验历史选择；指标、有效性、补测、保留及回滚由程序执行。界面展示选择与简要依据，不要求模型输出内部推理过程。此文是验证流程，不表示已经取得真实游戏收益。

## 自动化验证与规划对照

运行 `python -m unittest discover -s tests -v`。`tests/test_planning_feedback.py` 覆盖有效改善后的参考更新、无收益恢复后跳过动作、无效测量不被记成失败、历史影响模型选择、单候选免调用、模型异常回退及重启恢复；界面测试核对候选详情展开收起、来源和耗时。测试使用临时数据库与模拟接口。

在桌面“测试记录”打开任务，完成上一项恢复确认后，可以导出等待测试节点。任务编号是 SQLite 任务记录的 `task_id`；数据库默认位于 `.data/`，以下路径应替换为本机实际文件。导出包含任务、配置、候选和实验结论，请保留在本机；不包含 API 配置、密钥或原始逐帧采集。

```powershell
python -m tools.planning_evaluation --database .data/gametune.db --task-id <任务编号> --output .qa/checkpoint.json
python -m tools.planning_evaluation --input .qa/checkpoint.json --output .qa/local-evaluation.json
python -m tools.planning_evaluation --input .qa/checkpoint.json --model --output .qa/model-evaluation.json
```

最后一条命令显式调用环境变量配置的模型接口，使用已有的 `GAMETUNE_API_BASE`、`GAMETUNE_API_KEY`、`GAMETUNE_MODEL`，不要把凭据写进场景文件。输入也可以是多个快照组成的 JSON 数组。当前导出受控补测时只保留正在执行的候选，不允许对照工具替换它；等待恢复或任务完成时不能导出新实验节点。

两种规划使用相同的配置、证据、历史和合法候选。输出记录选中项、依据、调用来源、耗时、是否重复同一参考条件下已证明无收益的动作；模型失败回退与单候选不调用分别标注，不计作成功模型选择。对照不会改变任务或应用设置。候选先经过游戏规则校验，但“合法”不等于“最优”。

若需要人工判断选择是否合理，在输入快照增加 `acceptable_candidate_ids` 列表，填写候选对应的 `plan_candidate_id`；该编号可从任务计划的 `planning_context.candidate_options` 或对照输出中获取。可以接受多个候选，先写清证据与画面代价标准再进行模型比较。输出的 `reviewer_acceptable` 仅代表场景评审者的标注，未标注时为空；`same_choice` 只表示选择相同，不能据此证明优劣。`model_comparison_available` 为 false 时不得将回退当成模型效果。

## 两个真实游戏案例

案例一验证有收益的调整。记录游戏版本、驱动、设备、场景路线、采集工具和模式、测试时长、原设置及目标；相同条件采集两次基线，差异超过 5% 时补第三次。保存原始采集文件并通过桌面导入，记录候选与选择理由，只执行指定调整，筛选后累计足够的有效测试，由程序确认是否保留，再保存下一步计划和报告。如果没有达到收益标准，如实归入无收益案例，不能挑选某一次高帧率作为成功证据。

案例二验证无收益回滚或证据不足补测。沿用相同采集口径，完整保留没有改善、退步、配置不一致或波动过大的记录，按程序提示补测或恢复，并确认后续计划如何变化。检查无收益动作不被重复、无效测量不被当成收益或失败、恢复前不会开启新实验。对于同一方案的补测，检查配置和比较基准保持一致。

每个案例应保留原始 CSV、基线与候选配置、逐次运行数据、程序结论和理由、恢复确认以及前后两次规划快照。可以在多个节点导出快照，使用同一批快照比较本地规则与在线模型，分别报告合理选择、重复动作、回退次数和耗时。即使数据来自真实采集，对照仍是规划回放，不能证明未实际执行候选的性能收益。

目前自动化测试只能验证程序闭环，真实案例需要在实际游戏中采集，在线模型选择也需单独运行上述命令或桌面流程。不要把模拟测试、用户录入值或回放输出改称已完成的真实游戏验证。
